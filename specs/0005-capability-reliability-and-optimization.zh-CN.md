# SDD 0005：功能、可靠性、工程可用性与自优化

状态：**G1–G3 已在声明的支持域与工作负载内实施并通过验收；G4 未启动**。日期：2026-11-09。[英文契约](0005-capability-reliability-and-optimization.md)。

目标是在明确支持的建模/装配场景中，由 Colocad 独立承担 CAD 基础栈职责；不据此宣称已经完整替代 CadQuery/build123d。Agent、harness、SDK 和 native 均在同一个沙箱里运行。SDD 0004 继续约束查询/基准/接口的细节，本规范定义整体执行顺序。

## 四个目标，严格依次验收

| 目标 | 必须完成 | 通过证据 |
| --- | --- | --- |
| **G1 功能覆盖** | 通用有界选择、拓扑查询、几何基准、配合、孔/孔组、安装接口，以及 SDK/CLI/tool | 每项公开能力都有正反例和 schema；外部 STEP → 选择 → 基准/接口 → 装配 → 精确检查贯通。手写坐标例子不能替代此验收。 |
| **G2 几何可靠性** | 复杂布尔、圆角、薄壁、曲面、外部 STEP 的真实与困难用例 | 先冻结带来源/许可/哈希的语料、分族要求和验收阈值；独立回读验证；报告成功、失败与正确拒绝的分母。必需用例通过，不能隐去必需特征。 |
| **G3 工程可用性** | 改参和替换保持语义意图，拒绝陈旧引用，诊断与恢复，并验证沙箱资源 | 编辑/拓扑变化/替换序列，重新打开与迁移，对称歧义，session 恢复，真实 agent 工具轨迹，以及 Linux arm64 1 vCPU / 512 MiB 下的明确资源口径。 |
| **G4 benchmark 与回溯优化循环** | 自动组织测量、归因、最小复现、提出修复、独立验证和回归 | 只有前三阶段有有效验收证据才进入；每个候选都有可回放记录，失败和退步也保留。 |

顺序是 **G1 → G2 → G3 → G4**。开发中的 TDD、输入限额、独立抽查和失败记录持续进行，它们不等于提前开展第四阶段的性能优化竞赛。发现正确性问题先修正确性。SDD 0004 的 M0–M3 用于组织 G1 的模块实现，其中生命周期、替换和资源验收也为 G3 提供证据；旧实验通过一部分不能跳过整阶段。

## “自优化”具体如何执行

这里指 agent 驱动的**代码、skill 和工具改进循环**，不是自动训练模型权重。每轮有以下闭环：

1. **固定基线**：源码/native/SDK/内核/编译器/依赖、硬件限额、用例与验证器全部固定。涉及推理时同时固定模型、提示、skill、tool 和预算。
2. **成对运行**：性能主对照是 **build123d**，要求相同几何、精度、验证和交付。OCCT 独立回读与其耗时单列。脚本调用和真实 agent 建模分别统计。
3. **定位原因**：按材料理解、特征、选择、基准、求解、检查、快照、STEP、三角化、渲染和宿主开销拆分；不能从总耗时猜瓶颈。
4. **回溯复现**：重放上一次通过的参数/来源，找到首个出错特征、约束或退步提交，缩成仍能复现问题的小用例，同时保留整机回归。
5. **单假设修复**：记录预期机制和影响面，形成独立变更。快速路径必须有几何适用条件与正确回退，不能按用例名或零件模板作弊。
6. **先验正确性**：最小复现、受影响族、冻结回归集和独立回读全部通过。少做圆角、放宽容差、吞掉歧义或降低表示精度，均不能记作优化。
7. **再验收益**：按固定冷/热口径重测并挑战保留集，报告噪声、退步与权衡。收益必须可重复，不能挑最好的一次或最有利的零件。
8. **接受或回退**：正确性/资源门槛未过则拒绝；无明确收益则保留旧基线。接受的结果成为下一版不可变基线，历史数据不覆盖。

## 防止对 benchmark 过拟合

调试复现集、冻结回归集、保留产品/参数组合分开，调优前记录划分。每个用例保留来源、许可、哈希、单位、参数、要求、允许简化、验证器及阈值。真实尺寸的指定/推导/假设/未知状态分开。困难用例失败后不得偷偷删掉用例、调整验收或把不支持算成成功。

指标先报告成功、正确拒绝、不支持、崩溃、超时、OOM，再报告耗时。改参引用稳定性、尺寸/材料/位置误差、缺失特征和错误接口接受率属于硬门槛。Agent 轨迹还记录修复次数、工具调用、token/费用与预算内成功率。

分别统计 time-to-STEP、time-to-preview、快照/加载/选择/求解/检查。至少五次新进程与五次重复操作，报告中位数、样本数、波动与最坏值，小样本尾分位明确标注。内存以 cgroup 峰值及 OOM 为主，注明子进程和缓存页；RSS 只能作为补充。CAD 单独和含驻留 agent/harness 的全流程预算分开。

速度、内存、失败率和推理成本共同判断；更快但超出内存预算仍失败。已有平板实验的十倍速度不能直接变成新任务的承诺。

## 记录与现状

每轮保留 ID、父基线、阶段验收状态、假设、用例划分/哈希、环境/命令、源码/二进制/skill 摘要、原始运行、逐阶段轨迹、最小复现、独立验证、差异、回归/保留集结果，以及接受/拒绝/不确定的理由。用例、来源、验证器或阈值变化要使相关证据失效，不能沿用旧通过标记。

未来 runner 在 G1–G3 任一证据缺失、过期或失败时必须拒绝 G4 的结果晋升。目前第四阶段是明确协议，尚未实现或启动为自动优化服务。

G1 支持域已验收，功能、外部 STEP 与完整产品证据保留在 [G1 台账](experiments/0004/README.md)。G2 冻结语料 24/24 通过（18 个正例、6 个正确拒绝）。G3 完成语义引用生命周期、替换、真实进程中断恢复、执行指纹缓存失效、有界解析器探测和两条真实 Pi 推理任务。最终回归为 127 项 Rust、macOS 与受限 Linux 各 41 项 Node、6 项脚本集成测试；Linux 语料与真实任务交付均通过独立 OCCT 回读。详见 [G2/G3 验收记录](experiments/0005/README.md)。

Agent、harness、SDK 和 native 同处 Linux arm64 1 vCPU / 512 MiB 沙箱；82 实体产品任务峰值 370.57 MiB，无 OOM。这是指定负载的实测验收，不是任意输入内存上限或全工业 CAD 等价声明。G4 未启动；npm alpha.6 尚不包含本轮开发变更，源码验收与发版分开记录。
