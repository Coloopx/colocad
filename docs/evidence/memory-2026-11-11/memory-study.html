Memory limits are a pipeline problem

Colocad alpha.8 · CadQuery 2.8.0 · build123d 0.13.0 — native Linux arm64, 1 vCPU, no swap.

Read the comparisons correctly

Common runs deliver exact STEP and validate analytic geometry. Policy refusal is not a low-memory success. A cgroup peak includes charged file pages; anonymous memory is reported separately. Three-run ranges are descriptive, not confidence intervals.

The indexed history test uses synthetic metadata, not hundreds of thousands of actual CAD edits. Chunking preserves geometry in an indexed project but does not produce one merged assembly STEP. No claim of O(log N) total resident exact geometry is made.

What the experiments establish

The same 2,048 distinct-part task completes at a 4 GiB cap with 2,289 MiB (CadQuery) / 2,312 MiB (build123d) peak, but both exceed a 2 GiB cap during STEP export. Colocad is efficient for shared instances; it uses more memory on the tested 64 distinct parts and 1,024-hole solid.

In the history plots, sdk is the current Node JSON-ledger lookup, indexed-node is the same Node runtime and SDK import with SQLite, and indexed is an auxiliary Python/SQLite control. Compare sdk with indexed-node to isolate the indexing change. A runtime_oom is V8 heap exhaustion, distinct from a cgroup oom.

194 executed observations; 6 larger cases unrun after a boundary. Agent, harness, inference and browser are outside these measurements. Wall times are descriptive on a shared host. Alpha.9 is planned; the indexed and chunked prototypes are not released SDK functionality.
